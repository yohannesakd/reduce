# Map a feature

Describe the feature: what it does, who uses each result, and what it is for. This step describes. It does not judge whether the target needs a result: the design step does that with every map record.

1. **2.1** Read the feature's tests and comments, and the documents that help you understand it: documentation, decision records, and agent instructions. The scope record lists the sources of the whole target. The code decides what the feature does. A document can be stale: use it only where it explains the code, and do not record where it differs from the code.
2. **2.2** Read the history of the feature's code with `git log -S`, `git log -G`, and `git blame`. Search it for migration, legacy, compatibility, workaround, fallback, and TODO markers. Record what each one explains, and why each part was added.
3. **2.3** Trace the feature from its entry points: types, callers, owners, readers and writers, state, boundaries, failures, and recovery paths. Include unchanged callers. Outlines and tool output alone do not answer this. Name two kinds of function in the entry of the result that the function produces. One kind has one call site. The other has callers that use different parameters, branches, or results. Step 1 of the [refactoring check](../../checks/every-feature/refactoring.md) uses the first kind: "Inline every function that is only used once and tighten former call sites". Step 4 uses the second kind: "Co-optimize multi-consumer functions with their callers".
4. **2.4** Make the inventory of the feature's results: what a caller, user, operator, test, or other program can observe. Give each result one entry: a return value or output, an error or message, a log line or metric, a stored or sent effect, an ordering or timing guarantee, a resource limit, or a configuration option and its effect. A branch, guard, default, fallback, retry, or special case gets no entry of its own. Name it in the entry of the result that it produces. For the code playbook, include each result that the change adds, removes, or changes. Cite the code of each result.
   - Entry: `B4 | A request without a token fails with "missing token" and sends nothing; the login screen shows the message | src/auth.ts:51-55; src/login.tsx:30`
   - Not an entry: `finish returns unless the sample is current`. That restates a line. Record the result that the line protects, such as "each press is recorded once".
5. **2.5** In each entry, name each consumer of the result and what the consumer does with it: shows, sends, stores, or decides something, or discards it. Cite the tests, documents, or callers that use the result. When you find no consumer, search tests, callers, configuration, and documentation by behavior and by symbol. Then write `no consumer found` and cite the search. When you cannot establish the consumers, write `consumers unknown` and the reason.
6. **2.6** When the feature has state that changes over events, such as jobs, queues, retries, migrations, sessions, or caches, write a table of every state, every event that moves it, and every reader, in the `finding` field of this instruction. Include scheduler, operator, timeout, and recovery events. Otherwise, record why the feature has no such state.
7. **2.7** In `## Intent`, state what the feature is for, in one paragraph: what it gives, to whom, and why it was added. Use the goals that the scope record quotes (`S<n>`), the commits that added the feature, and the consumers of its results. Label a deduction from the code as an inference. Then name each part whose reason you did not find: a result with no consumer, a mode or an option with no use that you can see, or code for a case that no source names. State these facts only. Do not judge whether the target needs a part.
8. **2.8** In `## Questions`, write the questions that only the user can answer and that decide whether a part is needed: who uses a result, whether a mode is still in use, or what a part is for. Write at most three, largest part first. Record what you found for each, and write `unanswered` as the answer. In attended mode, the parent merges the questions of all the features, asks the user, and records the answers here.

List the entries in `## Inventory`. Give each entry the ID `B1`, `B2`, and so on. Later steps cite the entry IDs.
The reviewer gets this record and the code. Do not copy or paraphrase the code into the record. Write each entry in a few sentences. Propose no reduction, and record a defect only as the result that the code gives.
Every file in the feature's paths needs an entry that cites it, or a row in `## Unmapped` with the reason.
